为什么会这样

app.wxss 里有一处全局盒模型重置，但它只覆盖了四个标签，漏了 input 和 textarea： 

view, text, scroll-view, image {
  box-sizing: border-box;
}   /* ← input / textarea 不在里面 */

而 .textarea 又写了 width: 100% + padding: 18rpx 26rpx + border: 1rpx。 默认盒模型下这 100% 只算内容宽度，padding 和边框是加在 100% 之外的， 所以实际宽度 = 343 + 26 + 1 = 370px，正好溢出 27px。

标题那个单行输入框没事，是因为它没写 width: 100%，宽度靠块级元素的 auto 计算，padding 会被自动扣掉。 —— 这也解释了为什么只有"有什么要交代的"这一栏看着不对。

已经改好了，都在 app.wxss：

- view, text, scroll-view, image {
+ view, text, scroll-view, image, input, textarea, button {
    box-sizing: border-box;
  }
  /* button 一起收进来：引导页/资料页用了 button.btn + width:100%，
     它有 padding: 0 28rpx，同一个坑，之前也溢出了 29px */

  .textarea {
-   min-height: 132rpx;
    padding: 18rpx 26rpx;
    border: 1rpx solid var(--line);
    border-radius: 24rpx;
    width: 100%;
+   display: block;
+   max-width: 100%;
+   box-sizing: border-box;
+   min-height: 170rpx;   /* 原 132 内容高 + 上下 padding 36 + 边框 2，视觉高度不变 */
  }

为什么要动 min-height：改成 border-box 后，132rpx 从"内容高度"变成了"含 padding 的总高"， 不改的话输入框会突然矮掉 38rpx。补到 170rpx 就是原来的视觉高度——这次只修宽度，不顺手改样子。

交互约定

选完立刻传，不等点发布。和"完成凭证"现在的做法一致——用户选完就能看到图，不用等到提交才知道成没成。 发布时只传 URL 列表，所以点发布是"瞬时"的。

上传中禁用发布，按钮文案变成「图片上传中…」。这点很关键：否则弱网下用户点得快，会把还没传完的临时路径存进库里，回头就是一张裂图。

6 张上限：一行放 4 格，6 张正好是一行满 + 一行两图带添加位。再多就该用聊天发了，而且上传等待时间会明显变长。

编辑任务时也能改图：现在的编辑模式（预约中 / 待接受，进行中只给一次）沿用同一套控件，改完会在时间线记一条"任务有变更"。

为什么不做九宫格

布置任务的图是"任务说明的一部分"，不是独立内容。它的阅读顺序是：标题 → 交代什么 → 图看细节。放在文字正下方，这个顺序天然成立。

换成九宫格区块的话，用户读到一个孤零零的图片网格，还得回头找是哪条任务的说明；而且小任务配大网格，页面会很空、很重。

什么时候再考虑九宫格

如果以后做到 9 张以上（比如"按这张清单采购"），才值得升级成独立图集。现在 6 张以内，横排 + 点开看大图就够了。

三个需要你定的

  1. 图片上限：我按 6 张设计的（一行 4 格，两行刚好）。6 张 / 3 张（和完成凭证一致） / 9 张，你选一个。
  2. 文字和图片的关系：我做成"同属交代，图是附件"。也可以做成必须写文字才能传图——但我觉得没必要，很多时候就是"图里那样"，一个字都不用写。
  3. 列表页要不要提示"有 2 张图"：现在列表卡片只有标题 + 头像 + 时间。我倾向不加，列表已经有"交代"两个字，点进去自然能看到。加了反而让卡片更挤。
