# 订阅消息机制说明

> 面向：产品 / 开发 / 运营
> 结论先行：**微信的一次性订阅天生不支持「每次创建任务、每个人都必达」**。这不是实现问题，是平台规则。
> 本文讲清官方机制、当前实现，以及还能往哪个方向使劲。

---

## 一、一句话结论

你现在遇到的问题，根源在一句话：

> **订阅额度属于「收件人」，不属于「发件人」；而且是「按模板按次」消耗的，不是「按任务」。**

所以：

- A 创建任务时点了「允许」，**只让 A 自己能收到**，不能让 B 收到；
- A 授权 1 次，只能收到 1 条，**跟他创建了几个任务无关**；
- B 想收到通知，必须 **B 自己**攒额度，A 替不了。

---

## 二、官方两种订阅：只有一种能用

| | 一次性订阅 | 长期订阅 |
|---|---|---|
| 授权一次能发几条 | **1 条** | 不限 |
| 是否需要重复授权 | 每次消耗完都要重新授权 | 一次授权长期有效 |
| 开放范围 | 所有小程序 | **仅限特定行业类目**：政务民生、医疗、交通、金融、教育、体育、居民服务、房地产、生活服务等 |
| 主体要求 | 个人 / 企业都可以 | 实际审核中基本只给企业，且类目要对得上 |
| 本项目能否用 | ✅ 能用 | ❌ **拿不到** |

**为什么拿不到长期订阅**：本项目主体是**个人**，服务类目是工具/生活类，「任务委托与协作」不在长期订阅的开放类目里。这不是申请技巧问题，是类目白名单问题——个人主体连申请入口都不会出现。

所以本项目只能走一次性订阅，下面的所有结论都基于这个前提。

---

## 三、三条底层规则（决定了产品形态）

### 规则 1：额度属于「用户 × 模板」，一次授权 = 一条

用户在弹窗里点「允许」，服务端获得该模板的 **1 条**下发额度。发一条扣一条，扣完归零。

额度是**账号级**的，跟具体哪条任务**没有任何关系**。

### 规则 2：额度按模板独立计

「任务委托通知」的额度和「任务到期提醒」的额度是两个独立额度。
用户只授权了「委托通知」，那「到期提醒」一条都发不出去。

微信一次授权最多同时申请 **3 个模板**（`tmplIds` 上限 3），超了直接报错。

### 规则 3：额度是「收件人自己的」

A 点「允许」，只是让 A 自己具备了接收能力。这条授权对 B、C、D 全部无效。

**微信不提供「发件人替收件人申请」的能力**，这是硬限制。

### 补充：关于「总是保持以上选择」

弹窗底部有个勾选框「总是保持以上选择，不再询问」。用户勾了之后：

- 我们下次调 `wx.requestSubscribeMessage` **不再弹窗**，直接返回 `accept`，额度 **+1**
- 这是唯一能让用户「无感攒额度」的机制

⚠️ 但有一个关键限制：**接口不返回「用户是否已勾选」这个信息**。
返回值只有 `accept` / `reject` / `ban`，无法区分「刚弹窗点了允许」和「之前勾了总是保持所以静默通过」。
所以代码上**判断不出**用户是否开启了免打扰授权，策略只能靠「控制调用频率」来兜。

## 四、完整推演：A 派活给 B，到底谁能收到

假设模板已配置好，场景是 A 创建任务派给 B。

### 第 1 步：A 创建任务

A 在「布置任务」页点发布，代码在他点击的同一个回调里调：

```js
notifyApi.requestSubscribe(['TASK_ALL_DONE', 'TASK_REMIND'])
```

- A 点「允许」→ **A 的**「全员完成」额度 +1、「到期提醒」额度 +1
- **B 的额度仍然是 0**

紧接着服务端给 B 发「任务委托通知」→ **B 没额度，发不出去**，只在站内消息中心留一条。

> 这就是你感受到的「怎么派了活对方没收到」的真正原因。

### 第 2 步：B 打开小程序，接受任务

B 点「接受」时，代码调：

```js
notifyApi.requestSubscribe(['TASK_REMIND', 'TASK_ASSIGNED'])
```

- 这是 B **这辈子第一次**有机会授权，通过率最高的一刻
- B 点「允许」→ **B 的**「到期提醒」+1、「委托通知」+1

### 第 3 步：A 再创建第 2 个任务给 B

| 谁 | 模板 | 额度 | 能不能发 |
|---|---|---|---|
| A | 全员完成 | 1（第 1 次授权攒的） | 能发 1 条，发完归零 |
| A | 到期提醒 | 1 | 能发 1 条 |
| **B** | **任务委托通知** | **0**（第 1 步和第 3 步都没有 B 的授权动作） | **发不出去** |

**结论**：你连着创建 10 个任务派给 B，B 一条卡片都收不到——因为**没有任何一步是 B 在授权**。而 A 自己的额度，只够 A 收自己那 2 类通知。

### 第 4 步：额度用光之后

服务端调微信接口会返回 `43101`（用户拒收或额度用尽）。
我们的处理是：**标记该模板失效、静默降级**，不重试、不告警、不影响业务。

## 五、当前项目的实现

### 5.1 只做 4 个模板

| 模板 key | 通知内容 | 收件人 | 触发时机 |
|---|---|---|---|
| `TASK_ASSIGNED` | 任务委托通知 | 每个参与者 | 创建任务、追加参与者 |
| `TASK_REMIND` | 任务到期提醒 | 未完成的参与者 | 定时扫描（`deadline - remindMinutes`）、手动催办 |
| `TASK_COMPLETED` | 任务完成通知 | 委托人 | 任一参与者完成且任务未结束 |
| `TASK_ALL_DONE` | 全员完成通知 | 委托人 + 全体参与者 | `all` 模式最后一人完成 |

**只做 4 个的原因**：模板越多，用户要授权的次数越多，`requestSubscribeMessage` 一次最多 3 个，7 个模板得弹 3 次窗，通过率断崖式下降。所以「任务开始 / 任务变更 / 任务撤回」三种只走站内消息，不发微信卡片。

### 5.2 授权点（3 处 + 1 处手动）

| 位置 | 申请的模板 | 为什么放这 |
|---|---|---|
| `pages/tasks/create/index.js#submit` | `TASK_ALL_DONE` + `TASK_REMIND` | 创建者此刻最想知道「他们都做完没」「快到点了没」，动机最强 |
| `pages/tasks/detail/index.js#onAccept` | `TASK_REMIND` + `TASK_ASSIGNED` | **接受任务 = 承诺**，通过率最高的一刻 |
| `pages/tasks/index/index.js#onAccept` | 同上 | 列表页直接接受的分支 |
| `pages/mine/settings/index.js` | 单个模板手动订阅 | 用户主动补订 |

⚠️ 所有授权调用**必须是点按事件的第一个 `await`**，中间夹任何异步都会报
`requestSubscribeMessage: fail can only be invoked by user TAP gesture`。

### 5.3 记账与下发链路

```
用户点「允许」
  → services/notify.js#report()
  → POST /api/subscribe/record        （前端立即上报，不等页面 await）
  → t_wx_subscribe.remain_count +1

业务事件（派活/完成/到期）
  → TaskNoticeService 写 t_task_notice（站内，事实来源）
  → 事务 afterCommit 触发 WxSubscribePusher.pushAsync()
  → 独立线程池（core 1 / max 2 / queue 200，队列满即丢弃）
  → WxSubscribeService.send()
      ├─ 查 remain_count，<=0 → 直接跳过
      ├─ 调微信，errcode=0 → remain_count -1
      ├─ errcode=43101 → 标记该模板失效（status=0）
      └─ 其他 errcode → 只打 warn
```

**几个刻意的设计**：

- **绝不在事务里发 HTTP**：一次派活 10 个人 = 10 次 HTTP，单次超时 5s，最坏 50 秒卡死连接池。所以必须异步 + afterCommit（也避免事务回滚后发出幽灵通知）。
- **队列满就丢弃，不阻塞**：站内有兜底，宁可丢一条卡片，不能反向拖垮用户请求线程。
- **单批上限 50 条**：定时提醒作业一轮可能扫出上百个任务，微信有频控（`45009`），超出的只落站内。
- **`remain_count` 只是我方估算**：多端登录、上报丢失、用户在微信里关掉接收通知，都会让这个数偏高。**微信端才是权威**，所以 `43101` 必须当正常分支处理。

### 5.4 模板未配置时的行为

所有 `templateId` 为空字符串时：

- `requestSubscribe` 直接返回 `{ skipped: true }`，**不弹窗、不报错**
- 投递层 `getTemplate()` 返回 null，**安静跳过**
- 站内通知一切照旧

也就是说：**模板审核期间，整套代码是安全空转的**，不会打扰用户，也不会误发。

## 六、现状与目标的差距

| 你的期望 | 现实 | 差距性质 |
|---|---|---|
| 每次创建任务，每个人都收到通知 | 收件人没额度就一条都收不到 | **平台规则**，代码改不了 |
| 创建者授权一次，之后所有任务都能通知 | 授权只覆盖自己，且一次只管一条 | **平台规则** |
| 长期有效，不用反复授权 | 长期订阅不对个人主体开放 | **主体资质** |
| 通知必达 | 用户可随时在微信里关掉接收，我们无法感知 | **平台规则** |

**必须接受的产品定位**：微信卡片是「加分项」，**站内消息中心才是唯一 100% 可靠的主渠道**。
`t_task_notice` + 首页红点 + 消息列表，这条链路必须做准、做及时——它才是产品承诺。

## 七、还能往哪使劲（按投入产出排序）

### 方案 1：把授权点铺到「高频低打扰」的位置 ⭐ 推荐

现在只在「接受任务」时申请。可以再加到「完成任务」「打开任务详情」这些 TAP 场景，
但要**控制在每个会话最多弹一次**（本地记录，避免反复骚扰）。

- 用户如果勾了「总是保持」→ 每次调用静默 +1，额度自然攒起来
- 没勾 → 只弹一次，可接受

**收益**：活跃用户基本能覆盖住自己的通知；**成本**：前端小改 + 频率控制。

### 方案 2：接受任务时用文案引导「总是保持」 ⭐ 推荐

在授权弹窗前加一句说明，例如：

> 点「允许」并勾选「总是保持」，以后有人给你派活就会收到提醒

微信审核不允许「不授权就不能用」这类胁迫文案，但**说明性质的引导是允许的**。

**收益**：把一次性授权变成长期免打扰授权，等于变相拿到「准长期订阅」；**成本**：一句文案。

### 方案 3：强化分享链路（首次触达靠它，不靠订阅）

A 派完活后引导转发，B 点卡片直接进任务详情。

- 零成本、**必达**、可以带参数
- 详情页已有 `onShareAppMessage`，只需在发布成功后弹一个「转发给 TA」的引导

**收益**：解决「首次派活对方完全不知道」这个最大空洞；**成本**：一个引导弹层。

### 方案 4：将来主体转企业，再申请长期订阅

如果产品要正式运营，把主体换成企业、类目调到「工具-效率」或「生活服务」，
再去申请长期订阅。但要注意：**长期订阅的类目白名单里没有「任务协作」这种描述**，
实际能不能过取决于审核对类目的认定，不能当作确定路径。

## 八、错误码速查

| errcode | 含义 | 我们的处理 |
|---|---|---|
| `0` | 成功 | 额度 -1 |
| `43101` | 用户拒收 / 额度用尽 | 标记模板失效，静默降级（**正常分支，不是异常**） |
| `47003` | 模板参数不匹配（关键词对不上） | 打 warn，需人工核对 yaml 与微信后台 |
| `40037` | template_id 无效 | 打 warn，检查配置 |
| `41030` | page 路径不存在 | 打 warn，检查 `page` 拼接 |
| `45009` | 接口调用超频 | 打 warn，检查单批上限 |

## 九、上线前检查清单

## 附：一句话给产品同学

> **订阅消息不是「通知功能」，是「用户主动领取的通知券」。**
> 券发给谁、谁才能用；一张券只能用一次。
> 我们能做的是「在用户最想收到消息的那一秒，请他领一张」，
> 做不到「让通知必达」——必达这件事只能靠小程序内的消息中心。
