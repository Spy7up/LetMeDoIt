# 订阅消息 v2 · 设计方案

> 目标：让**创建者**能收到任务的状态变化（接受 / 拒绝 / 完成 / 逾期），并且支持**多次**通知；
> 同时提供「创建后一键分享卡片给好友，点开直达详情页」的闭环。
>
> 本文先回答「能不能做」，再给机制、模板、额度和落地清单。

---

## 一、先回答：这个需求能做吗

### 结论

| 需求 | 能否实现 | 限制来源 |
|---|---|---|
| 创建者收到「接受 / 拒绝 / 完成 / 逾期」四类状态通知 | ✅ 能 | 需要新申请 1 个模板 |
| **同一个任务收到多次通知**（3 人分别接受 = 3 条） | ⚠️ 能做，但**发不满** | 一次性订阅：1 次授权 = 1 条额度 |
| 每次创建任务、每次状态变化都必达 | ❌ 做不到 | 平台规则，属于个人主体天花板 |
| 分享卡片直达详情页并接受/拒绝 | ✅ 完全能做 | 无平台限制 |

**一句话**：需求本身是合理的，技术上全部可落地；唯一要接受的是「额度是稀缺资源」，
所以设计的核心不是"发什么"，而是**"额度不够时先发哪条"**。

### 为什么不能"每条都发"

一次性订阅的额度是 **1 次授权 = 1 条**。一个派给 3 个人的任务，如果每条状态变化都发：

```
3 次接受 + 3 次完成 + 1 次逾期 = 7 条
```

创建者要攒 7 次授权才能收全。而用户不可能为每个任务点 7 次「允许」。

**所以要换思路**：不是想办法多要额度，而是**把 7 条压缩到 2~3 条关键通知**。

## 二、机制设计：4 个模板覆盖两个角色

### 2.1 模板重新划分

模板总数**仍然是 4 个**（容量不变，但语义重排）。关键改动：**新增 1 个「任务进展通知」给创建者，用它一网打尽 4 种状态**。

| 模板 key | 模板名 | 收件人 | 承载什么 |
|---|---|---|---|
| `TASK_ASSIGNED` | 任务委托通知 | 参与者 | 有人给你派活 |
| `TASK_REMIND` | 任务到期提醒 | 参与者 | 快到点了 |
| **`TASK_STATUS`** ⭐新增 | **任务进展通知** | **创建者** | **已接受 / 已拒绝 / 已完成 / 已逾期（四合一）** |
| `TASK_ALL_DONE` | 全员完成通知 | 创建者 + 全体 | 全部做完了 |

原来的 `TASK_COMPLETED`（有人完成了）**合并进 `TASK_STATUS`**，不再单独占一个模板。
这样创建者只需要授权 **1 个模板** 就能收全所有状态，而不用为每种状态单独授权。

### 2.2 `TASK_STATUS` 字段设计

```
thing1   任务名称      ≤20 字
phrase2  进展状态      ≤5 汉字   → 已接受 / 已拒绝 / 已完成 / 已逾期
thing3   相关的人      ≤20 字    → 小明
time4    发生时间      yyyy-MM-dd HH:mm
```

四个状态值全部 ≤5 个汉字，符合 `phrase` 类型限制 ✓

**申请场景说明**（审核主要看这段）：

> 用户在小程序内委托好友完成一件事，任务被接受、拒绝、完成或超时未完成时，
> 需要即时告知委托人以便其跟进。消息仅包含任务名称、进展状态、相关人员和时间，
> 不含任何营销内容。点击进入小程序对应任务详情页。

### 2.3 授权分工：每个角色一次弹窗搞定

微信一次 `requestSubscribeMessage` 最多 3 个 `tmplIds`。按角色分：

| 谁 | 什么时候 | 申请哪 2 个 | 为什么是这个时机 |
|---|---|---|---|
| **创建者** | 点「发布」时 | `TASK_STATUS` + `TASK_ALL_DONE` | 此刻他最关心"他们接了没、做完了没"，动机最强 |
| **参与者** | 点「接受」时 | `TASK_ASSIGNED` + `TASK_REMIND` | 接受 = 承诺，此刻他最怕"忘了做"，通过率最高 |

两边各 2 个，都在 3 个上限内，**一次弹窗完成，不需要弹第二次**。

## 三、额度：从「随机失败」变成「优先级调度」

### 3.1 额度从哪来（三条补给线）

| 补给点 | 收益 | 备注 |
|---|---|---|
| 点「发布」/「接受」时授权 | +1 | 主入口，通过率最高 |
| **每次打开任务详情时静默补一次** | +1 | 依赖用户勾了「总是保持」，不弹窗 |
| 点「催一下」时补一次 | +1 | 主动行为，弹窗可接受 |

**关键**：如果用户勾了弹窗底部的「总是保持以上选择」，之后每次调用都**静默 +1**，不打扰。
一个每天开 3 次小程序的创建者，每天能攒 3 条左右额度 —— 够覆盖 1~2 个任务的关键通知。

⚠️ 但接口**不返回用户是否已勾选**，所以补授权必须做频率限制（同一会话最多 1 次），否则会反复弹窗惹人烦。

### 3.2 通知分级：额度不够时按这个顺序发

| 优先级 | 通知 | 理由 |
|---|---|---|
| P0 | **有人拒绝了** | 任务卡住了，创建者必须马上知道并处理 |
| P0 | **任务逾期了** | 需要立即决策（催办 / 放弃） |
| P1 | **全员完成** | 任务闭环，情绪价值最高 |
| P2 | **有人完成了（部分）** | 信息性，聚合后发 |
| P3 | **有人接受了** | 纯信息，**只在"全部接受完毕"时聚合发 1 条** |

实现上：投递前查剩余额度，额度 <= 0 时**只丢 P2/P3**，P0 走站内强提醒（红点 + 首页置顶）。

### 3.3 聚合：把 7 条压到 2~3 条

| 原始事件 | 处理 |
|---|---|
| 参与者 A 接受 | 不立即发，攒着 |
| 参与者 B 接受 | 不立即发，攒着 |
| 参与者 C 接受 → **全部接受完毕** | 发 1 条：`phrase2=已接受`、`thing3=C`、`thing1=任务名` |
| 参与者 A 完成 | 发 1 条：`phrase2=已完成`、`thing3=A` |
| 参与者 B 拒绝 | **立即发**：`phrase2=已拒绝`（P0，不等聚合） |
| 全部完成 | 发 `TASK_ALL_DONE` |
| 超过 deadline 仍未完成 | 发 1 条：`phrase2=已逾期`（每任务只发一次） |

**一个 3 人任务的实际消耗：2~3 条**（原来要 7 条）。

### 3.4 一个额外保险：5 分钟去重窗口

同一任务、同一状态、5 分钟内只发一条。
防止用户手抖连点（比如连续催办、反复接拒绝）导致额度被瞬间打光。

## 四、需求 2：分享卡片直达详情页

### 4.1 链路

```
A 创建任务成功
  → 弹「已发布，告诉 TA 一声」引导层（带任务标题 + 参与者头像）
  → 点「发给 TA」→ 调起微信转发面板（button open-type="share"）
  → B 在聊天里收到卡片：「A 让你做：晾衣服 · 今天 21:00 前」
  → B 点卡片 → 直接进 /pages/tasks/detail/index?id=xxx&from=share
  → B 看到「A 托你做这件事」+ 底部「拒绝 / 接受」
  → B 点接受 → 任务进入进行中（A 那边收到 TASK_STATUS 通知）
```

### 4.2 分享入口放三处

| 位置 | 形态 | 说明 |
|---|---|---|
| **创建成功后的引导层** | 主按钮「发给 TA」 | 最高频、最自然，**核心入口** |
| 任务详情页右上角 | 页面内 `<button open-type="share">` | 随时补发 |
| 任务卡片长按 | 转发 | 微信原生能力，零成本 |

⚠️ 小程序只能用 `<button open-type="share">` 触发转发，`<view bindtap>` 调不起来。
所以按钮必须是 `button` 元素，并且要覆盖 `button.btn` 的默认宽度（我们已经有这个处理）。

### 4.3 卡片内容

```
标题：{创建者} 让你做：{任务标题}
     有截止时间时追加 → 「 · 今天 21:00 前」
图片：任务附图第一张（5:4 裁切），没有图就用默认封面
路径：/pages/tasks/detail/index?id={taskId}&from=share
```

标题长度控制：微信卡片标题超过 2 行会截断，所以任务名超过 12 字时只保留前 12 字 + 省略号。

### 4.4 落地页要处理的 4 种人

| 点开的人 | 看到什么 |
|---|---|
| **是参与者，且待接受** | 强化版接收态：「A 托你做这件事」+ 「拒绝 / 接受」按钮 |
| 是参与者，已接受 | 正常详情 + 「完成我这份」 |
| 是创建者自己 | 正常详情（分享给自己兜底） |
| **不是参与者**（转发给了第三方） | 只读详情 + 底部提示「这不是交给你的任务」+ 「让 TA 也加我」 |

最后一种必须有兜底，否则转发到群里，一群人点进来看到空白页，体验很糟。

### 4.5 冷启动的坑

分享卡片点进来是**直接进入目标页**，不经过 `pages/launch/index`（登录页）。所以详情页的 `onLoad` 必须自己处理登录：

```js
async bootstrap() {
  await getApp().ensureLogin()   // 已有 ✓
  this.load()
}
```

这一点现有代码已经做对了，不用改。

## 五、数据与接口变更

### 5.1 通知类型

`NoticeTemplateEnum` 新增 3 个（前两个走微信，第三个只站内）：

| key | 标题 | 走微信 |
|---|---|---|
| `TASK_ACCEPTED` | 任务被接受 | ✅ `TASK_STATUS` |
| `TASK_REJECTED` | 任务被拒绝 | ✅ `TASK_STATUS` |
| `TASK_OVERDUE` | 任务已逾期 | ✅ `TASK_STATUS` |

> 三个 key 共用同一个微信模板 `TASK_STATUS`，靠 `phrase2` 区分。
> 这样站内消息能精确分类（消息中心显示"小明拒绝了「晾衣服」"），微信卡片复用同一模板节省额度。

`TASK_COMPLETED` 保留，但**不再单独配置微信模板**，内容并入 `TASK_STATUS`。

### 5.2 触发点

| 事件 | 现在 | 改动 |
|---|---|---|
| 接受任务 | 只写站内 | 新增 `notifyAccepted` → 创建者 |
| 拒绝任务 | 只写站内 | 新增 `notifyRejected` → 创建者 |
| 完成任务 | `notifyCompleted` → 创建者 | 改为写 `TASK_STATUS` 类型 |
| 逾期 | **没有** | 定时作业新增扫描 + `notifyOverdue`（每任务只发一次） |

逾期扫描：`status = 进行中 AND deadline < now AND 无 TASK_OVERDUE 通知`。
用 `t_task_notice` 查重即可，不需要加字段。

### 5.3 投递层要加的能力

`WxSubscribePusher` 目前只做「按模板装箱 → 发送」。v2 需要加：

1. **优先级参数**：`pushAsync(notices, priority)`，额度不足时按 P0 > P1 > P2 > P3 决定丢弃顺序
2. **聚合判定**：`TASK_ACCEPTED` 不直接发，转为检查"是否全员已接受"，是则发一条
3. **5 分钟去重**：查 `t_task_notice` 同任务同 templateKey 的最近一条

## 六、风险与限制（务必先接受）

| 风险 | 影响 | 应对 |
|---|---|---|
| 创建者没攒够额度 | 部分甚至全部状态通知发不出去 | 站内消息中心兜底 + 优先级调度保证"最要紧的先发" |
| 用户没勾「总是保持」 | 每次补授权都弹窗，会被投诉 | 严格限制频率：同一会话最多补 1 次 |
| 无法感知用户关掉了微信通知 | 我们以为能发，实际 43101 | 把 43101 当正常分支，静默标失效 |
| 模板审核被拒 | 整个 v2 不生效 | 先提交申请，代码按"空 id 安全空转"写，模板下来只改配置 |
| 分享卡片被当成骚扰 | 用户体验差 | 只在创建成功后引导一次，不做自动化打扰 |

**产品定位不变**：微信卡片是「关键时刻的加成」，`t_task_notice` + 首页红点才是**唯一 100% 可靠的主渠道**。

## 七、落地清单（分两期）

### 第一期：分享卡片（零依赖，可立即做）

- [ ] 创建成功后改为弹「已发布」引导层，主按钮「发给 TA」（`button open-type="share"`）
- [ ] 详情页顶部加分享按钮（同 `open-type="share"`）
- [ ] `onShareAppMessage` 优化：标题带截止时间、图片用附图首张、path 带 `from=share`
- [ ] 详情页识别 `from=share` + 参与者待接受态 → 显示「A 托你做这件事」强化条
- [ ] 非参与者进入 → 只读 + 「这不是交给你的任务」提示
- 工作量：前端 3 个页面，后端 0 改动

### 第二期：状态通知（等模板审批）

- [ ] 申请 `TASK_STATUS` 模板（字段见 2.2）
- [ ] `NoticeTemplateEnum` 加 `TASK_ACCEPTED` / `TASK_REJECTED` / `TASK_OVERDUE`
- [ ] `TaskNoticeService` 加 3 个 notify 方法，接在 accept / reject / 完成 / 逾期扫描处
- [ ] `TaskScheduleJob` 加逾期扫描（每任务只发一次）
- [ ] `WxSubscribePusher` 加优先级 + 聚合 + 去重
- [ ] 创建者授权点改为 `TASK_STATUS` + `TASK_ALL_DONE`
- [ ] 详情页/列表页进入时静默补授权（频率限制）
- [ ] 设置页展示「任务进展通知」额度
- 工作量：后端 5 处 + 前端 3 处

## 八、一句话总结

> **不要去追「每条都发」，要追「最要紧的那条一定发出去」。**
>
> 4 个模板、两个角色各一次弹窗、P0/P1/P2/P3 四级优先级、5 分钟去重、
> 把 3 人任务的 7 条状态通知压到 2~3 条 —— 这是在个人主体天花板下能做到的最优解。
>
> 分享卡片则是另一条完全不同的路：**它不受额度限制、100% 必达**，
> 所以「首次触达」这件事应该交给分享，而不是订阅消息。
