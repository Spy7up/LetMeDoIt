# 《让我做》v1.1 产品与技术方案

> 版本 v1.1 · 2026-10-20 · 微信小程序 · 前端先行（SpringBoot + MySQL + Redis 后端本阶段不实现）
> v1.1 变更：① 首页液态玻璃 banner；② 多参与者与两种完成条件；③ 与微信「服务通知」同构的通知体系。
> 本文档是后续编码的唯一依据：页面路由、数据结构、接口签名、组件与状态均已定稿，编码时不再二次设计。

---

## 1. 产品定位

### 1.1 一句话

**别人让你做的小事，说一遍就够。**

「让我做」是给熟人关系（家人、室友、情侣、好友）用的**口头委托承接箱**：妈妈喊你晾衣服、室友让你带瓶酱油、朋友托你帮取快递——说出口的那一刻就落成一条任务，自动提醒相关的人，做完对方第一时间知道。

### 1.2 它解决的问题

| 现状痛点 | 产品对策 |
|---|---|
| 微信里口头交代，消息一刷就没 | 委托落成结构化任务，不依赖聊天记录 |
| 谁该做什么、什么时候要，全靠记 | 截止时间 + 订阅消息提醒，到点必达 |
| 催人尴尬，问"弄了吗"像查岗 | 状态即答案：谁在做、谁做完了，不必开口问 |
| 一句"你俩一起弄一下"，最后只有一个人动 | 多人任务 + 每人独立完成状态，谁没动一目了然 |
| 做了没人知道，没有正向反馈 | 完成后自动通知委托人，形成"被看见"的闭环 |
| 通用待办 App 是"自己的事"，没有关系维度 | 任务天生绑定几个人，社交压力即执行力 |

### 1.3 差异化（决定 UI 取舍）

1. **以"关系"组织，不以"项目"组织**。没有列表、标签、看板，只有"我收到的 / 我发出的"。信息架构只有两层：任务列表 → 任务详情。
2. **多人不是"协作"，是"分摊"**。一条任务可以交给 1~10 个人，每个人只管自己那一格，不存在子任务拆解和互相指派。这是"家务"和"项目管理"的根本区别。
3. **双方视角对称**。同一个任务在委托人眼里是"我在等"，在参与者眼里是"我要做"，因此列表项文案、按钮、颜色随角色变化。
4. **文案去企业化**。不用"负责人""验收""逾期未处理"，用"等 TA 接单""我这部分做完了""催一下"。
5. **轻量优先**。布置一条任务 ≤ 4 次点击（选人、写标题、选截止、发布），其余全部有默认值。

### 1.4 明确不做（v1.1 边界）

- 不做**群聊式协作**：任务下没有讨论区、没有 @、没有评论流，沟通仍回微信
- 不做**子任务拆解 / 互相指派**：参与者之间是平级的"各做一格"
- 不做重复任务（每天/每周）、优先级、标签
- 不做积分、排行榜、打卡日历
- 不做陌生人社交，好友必须先建立关系

## 2. 用户角色与关系模型

### 2.1 角色

| 角色 | 定义 | 权限 |
|---|---|---|
| 未登录访客 | 首次进入、未授权 | 仅可浏览引导页，任何写操作跳登录 |
| 登录用户 | 已微信登录并完成资料 | 全部功能 |
| 委托人 Creator | 某条任务的布置方（一条任务只有一个） | 编辑（未开始前）、撤回、催办、加人、查看所有人的进度与备注 |
| 参与者 Participant | 被委托人指定执行的人（1~10 个） | 接受 / 拒绝（仅自己那格）、标记自己完成（附备注与凭证）、查看其他参与者状态 |

两条关键规则：

1. **角色是任务维度的，不是账号维度的**。A 让 B 晾衣服时 A 是委托人；B 让 A 带饭时 B 是委托人。
2. **委托人可以把自己加进参与者**。"我们一起把这事干了"是家庭场景的高频表达，不额外开一条任务。此时同一人在任务里同时拥有两套权限（可撤回 + 可完成自己那格）。

### 2.2 好友关系

- 双向对等，一条 `t_friend` 记录代表一对关系（存储时双写两行，便于按 userId 查询）
- 建立方式：**分享邀请卡片**（主路径）或 **6 位邀请码**（面对面场景，如家里长辈）
- 解除关系：二次确认；已存在进行中任务时提示"你们还有 2 个任务没结束"，但不阻断

```
邀请方 A                     被邀请方 B
  │  生成邀请卡片/邀请码          │
  ├──────── 微信分享 ──────────►│
  │                             │  点击进入 → 确认添加
  │◄─────── 请求好友 ───────────┤
  │  同意                        │
  ├──── 双向关系建立 ────────────┤
```

### 2.3 用户画像（指导文案与默认值）

- **小宇 24 岁**，和室友合租。场景：让室友带东西、让室友帮忙收快递。偏好快，讨厌填表。→ 表单默认值必须合理，标题是唯一必填。
- **王阿姨 52 岁**，用小程序给孩子派活，习惯"你俩一起弄"。→ 多人选择要显眼，每人状态要看得懂，字不能小。
- **小林 29 岁**，异地恋。用任务维系日常（"提醒我 9 点吃药"→对方监督）。→ 定时任务与提醒是刚需。

## 3. 核心业务流程

### 3.1 主流程：一次完整委托（单人）

```
①  布置      委托人：选 1 个人 → 填标题/描述/截止/提醒 → 选「任一人完成」→ 发布
                        │  （发布前请求订阅消息授权）
                        ▼
②  待接受    参与者收到服务通知「任务委托通知」+ 列表红点
                        │
            ┌───────────┴───────────┐
       接受 ▼                       ▼ 拒绝（填理由）
③  进行中                            已拒绝（终态，委托人可"重新布置"复制新任务）
            │
            ├── 到点未完成 ──► 已逾期（红标 + 提醒消息）
            │
            ▼ 附备注/凭证，标记完成
④  已完成   委托人收到「任务完成通知」→ 可看凭证
```

### 3.2 主流程：多人委托的两种完成条件

```
委托人布置「周末大扫除」→ 选 4 个人 → 选完成条件

【所有人都要完成】                    【任一人完成即可】
  小王 ✓ 已完成                        小王 ✓ 已完成
  我    ● 在做        进度 1/4          我    ⊘ 无需参与    整单已完成
  阿哲  ● 在做                         阿哲  ⊘ 无需参与
  陈陈  ○ 待接受                       陈陈  ⊘ 无需参与
       ↑                                     ↑
  差 3 人，任务仍进行中                 谁先做完，这单就结束，
  最后一人完成 → 「全员完成通知」        其余人自动跳过（不追责、不再提醒）
```

选型建议（写进表单默认值与提示）：
- 派给多人做**同一件事**（晾衣服、搬桌子）→ 任一人完成
- 派给多人做**各自一块**（大扫除、各自房间）→ 所有人完成

### 3.3 定时任务（预约）

委托人可勾选「定时生效」，设定 `startAt`：

- 发布后状态为 `scheduled`，参与者列表中显示为"预约中"，**不可接受**（避免提前接单后遗忘）
- `startAt` 到点，后端把任务置为 `pending` 并推送「任务开始」消息
- 委托人可在 `pending` 之前撤回、加人、改条件

### 3.4 状态机（唯一定义源）

**两层状态**：
- **参与者状态**（`participant.status`）：每个人的独立进度，落库
- **任务聚合状态**（`task.status`）：由参与者状态 + 完成条件算出，**写入时重算并落库**，供列表筛选与通知使用

参与者状态转移：

| 当前 | 事件 | 下一状态 | 触发方 | 备注 |
|---|---|---|---|---|
| — | 被加入任务 | `pending` | 委托人 | |
| `pending` | accept | `accepted` | 该参与者 | |
| `pending` | reject | `rejected` | 该参与者 | 必填理由 |
| `accepted` | complete | `done` | 该参与者 | 可附备注/图 |
| `pending` / `accepted` | 他人完成且模式为 `any` | `skipped` | 系统 | 自动跳过 |
| `done` / `rejected` / `skipped` | — | 终态 | — | |

聚合状态计算（`aggregate(task)`，前后端各一份实现但**以服务端为准**）：

```
if (定时未开始 && 无人动作)              → scheduled
if (全部 rejected/skipped)               → rejected
if (全员 done)                           → completed
if (completionMode === 'any' && 有人 done) → completed
if (有人 accepted 或 done)               → in_progress
else                                     → pending
```

**逾期仍是派生，不是状态**：`displayStatus = overdue` 当 `status ∈ {pending, in_progress} && deadline < now`。查询 `status=overdue` 时服务端翻译为 `status IN (pending, in_progress) AND deadline < NOW()`。

例外：`cancelled` 由委托人直接写入，不参与聚合。

### 3.5 时间与提醒规则

| 项 | 规则 |
|---|---|
| 截止时间粒度 | 分钟；默认「今天 21:00」，可选今天/明天/后天/自定义 |
| 提醒方式 | 不提醒 / 提前 10 分钟 / 提前 1 小时 / 提前 1 天 / 自定义 |
| 提醒对象 | 参与该任务且状态为 `pending`/`accepted` 的人，**已完成/已跳过的人不打扰** |
| 提醒执行 | 服务端 Redis ZSet 延时队列，到期投递订阅消息 |
| 逾期判定 | `deadline < NOW() AND status IN (pending, in_progress)` |
| 逾期重复提醒 | 每 12 小时最多 1 次，最多 2 次 |
| 催办频率 | 同一任务每 60 分钟最多 1 次，每天最多 3 次 |
| 时区 | 统一东八区，服务端存 UTC，接口返回 ISO8601 字符串 |

### 3.6 异常与边界

| 场景 | 处理 |
|---|---|
| `any` 模式下有人完成，其余人怎么办 | 其余 `pending`/`accepted` 自动置 `skipped`，不再提醒；他们看到"已被小王完成" |
| 全部参与者都拒绝 | 聚合为 `rejected`，通知委托人"没人接，要不要换个人" |
| 部分人拒绝、部分人完成（`all` 模式） | 任务继续；`rejected` 的人不计入分母，进度显示 `done/(total-rejected)` |
| 委托人把自己加进参与者 | 允许。详情页同时显示"撤回/加人"和"完成我这份" |
| 好友已解除关系，仍有进行中任务 | 任务保留可完成，列表标注「已不是好友」，禁止新建 |
| 参与者已完成后想追加 | 禁止（`canAddParticipant=false`），避免已完成任务又冒出新待办 |
| 重复提交（网络抖动） | 前端按钮 loading + 幂等键 `clientRequestId` |
| 订阅消息授权被拒 | 不阻断发布，用 in-app 消息中心与角标兜底 |

### 4.3 路由与导航约定

- 详情页统一自定义导航栏（`navigationStyle: custom`），返回用 `wx.navigateBack`，无历史时 `reLaunch` 到任务页
- 创建页用 `navigateTo`，成功后 `navigateBack` + `eventChannel` 回传新任务，列表 `onShow` 静默刷新兜底
- 分享进入：`pages/tasks/detail/index?id=xxx` → 未登录先走 launch，登录后 `redirectTo` 回原路径
- 消息中心的卡片点击：`redirectTo` 到 `pages/tasks/detail/index?id=`，`fail` 时兜底 `reLaunch`

## 5. 数据结构

### 5.1 通用约定

- 所有 `id` 为 **string**（后端 Long 序列化为 string，规避 JS 精度丢失）
- 所有时间为 **ISO8601 字符串**（`2026-10-20T21:00:00+08:00`），前端统一格式化，禁止传时间戳数字
- 布尔字段以 `is/can` 前缀命名
- 接口返回统一信封：`{ code, message, data, traceId }`，`code === 0` 为成功

### 5.2 核心实体

```ts
interface User {
  id: string
  nickname: string
  avatarUrl: string
  inviteCode: string          // 6 位，用于加好友
  stats: UserStats
  createdAt: string
}

interface UserStats {
  sentCount: number           // 我布置的
  receivedCount: number       // 我被拉进去的
  completedCount: number      // 我完成自己那份的次数
  onTimeRate: number          // 准时完成率 0~1
  friendCount: number
}

// 参与者：任务里的"一格"
interface TaskParticipant {
  userId: string
  nickname: string
  avatarUrl: string
  status: ParticipantStatus   // pending | accepted | done | rejected | skipped
  completedAt: string | null
  remark: string              // 完成备注，≤200
  images: string[]            // ≤3
  rejectReason: string
}

// 任务详情
interface Task {
  id: string
  title: string                    // ≤30
  description: string              // ≤200
  creator: TaskUser                // 布置人
  participants: TaskParticipant[]  // 1~10，含委托人自己（若他也参与）
  completionMode: CompletionMode   // any | all
  progress: {                      // 服务端算，前端只展示
    total: number
    done: number
    accepted: number
    rejected: number
    skipped: number
  }
  status: TaskStatus               // 聚合状态
  startAt: string | null
  deadline: string
  remindType: RemindType
  remindMinutes: number
  isOverdue: boolean

  me: {                            // 我在这条任务里的那一格；非参与者为 null
    userId: string
    status: ParticipantStatus
    completedAt: string | null
    remark: string
    canAccept: boolean
    canReject: boolean
    canComplete: boolean
  } | null
  isCreator: boolean
  canCancel: boolean
  canRemind: boolean
  canAddParticipant: boolean
  canEdit: boolean

  createdAt: string
  updatedAt: string
  events: TaskEvent[]
}

// 列表项（轻量）
interface TaskListItem {
  id: string
  title: string
  status: TaskStatus
  isOverdue: boolean
  deadline: string
  role: 'assignee' | 'creator'     // 我在这条任务里是参与者还是纯委托人
  completionMode: CompletionMode
  participantCount: number
  progress: { total: number; done: number }
  participants: TaskParticipant[]  // 最多 4 个，用于头像堆叠
  counterpart: TaskUser            // 委托人（发出的任务用于显示"我布置的"）
  myStatus: ParticipantStatus | null
  hasProof: boolean
  updatedAt: string
}

interface TaskEvent {
  id: string
  type: 'created' | 'invited' | 'scheduled' | 'started' | 'accepted'
      | 'rejected' | 'completed' | 'cancelled' | 'reminded' | 'expired'
  actor: TaskUser | null
  text: string        // 服务端生成的中文描述，前端直出
  createdAt: string
}

// 服务通知（与微信服务通知同构）
interface NoticeMessage {
  id: string
  templateKey: 'TASK_ASSIGNED' | 'TASK_REMIND' | 'TASK_COMPLETED' | 'TASK_ALL_DONE'
  taskId: string | null
  title: string                     // 模板标题，如「任务委托通知」
  fields: { label: string; value: string }[]   // 即卡片左侧标签 + 右侧值
  read: boolean
  createdAt: string
}

interface PageResult<T> {
  list: T[]
  unreadCount?: number
  nextCursor: string | null
  hasMore: boolean
}
```

type CompletionMode = 'any' | 'all'
type RemindType = 'none' | 'm10' | 'h1' | 'd1' | 'custom'
type Role = 'assignee' | 'creator'

## 6. 接口层设计

### 6.1 分层

```
pages/            ← 只做渲染与交互，不写 URL、不拼参数
  └ services/     ← 领域方法（task.accept / notice.list），返回领域对象
      └ utils/request.js  ← 统一信封拆包、token、重试、错误码、Mock 分流
          └ config/index.js ← BASE_URL、USE_MOCK、超时、环境、订阅模板
```

**铁律**：页面中不允许出现 `wx.request`、`/tasks/xxx` 字面量、`res.code === 0` 判断。
页面只写 `try { const task = await taskApi.complete(id, dto) } catch (e) { ... }`。

### 6.3 错误码

| code | 含义 | 前端行为 |
|---|---|---|
| 0 | 成功 | — |
| 40100 | 未登录 / token 失效 | 静默重新登录并重放一次，失败则跳登录 |
| 40300 | 无权限（非本人任务 / 非好友参与者） | toast「这不是你的任务」+ 返回 |
| 40400 | 资源不存在 | 空态页「任务已被删除」 |
| 40900 | 状态冲突（已接单又接、已完成又加人） | toast + 刷新详情 |
| 42200 | 参数校验失败 | 字段级错误提示（`data.field`） |
| 42900 | 请求过频（催办过多） | toast 服务端 `message` |
| 50000 | 服务端异常 | toast「出了点问题，再试一次」 |

### 6.4 Mock 策略

- `config.USE_MOCK = true` 时 `request.js` 不发网络请求，改调 `mock/server.js`
- Mock 层实现完整聚合逻辑与权限位，内置 280~620ms 延迟、可配失败注入
- 种子数据覆盖：7 种任务状态 × 单人/多人 × 两种完成条件 × `skipped` 分支，任一列表打开即有内容
- 切换真实后端只改 `config/index.js` 一行，`services/*` 与页面零改动

## 7. 通知体系（与微信「服务通知」同构）

### 7.1 平台约束先讲清楚

微信「服务通知」的卡片样式**完全由微信渲染，开发者无法改 CSS**。能控制的只有三样：

1. **模板标题**（如「任务委托通知」），对应卡片的大字标题
2. **关键词标签**（如 `thing1 → 任务名称`），对应卡片左侧灰字
3. **字段值**，对应右侧黑字

所以**模板设计就是界面设计**。下图是我们希望用户看到的样子（与参考截图结构一致）：

```
┌────────────────────────────────────────┐
│  (logo) 让我做                      ··· │
├────────────────────────────────────────┤
│  任务完成通知                            │
│                                        │
│  任务名称        周末大扫除               │
│  完成人          小王                    │
│  完成时间        2026-10-20 22:16        │
│  完成进度        1/4 人已完成             │
├────────────────────────────────────────┤
│  进入小程序查看              ◉ 小程序 ›  │
└────────────────────────────────────────┘
```

四条设计纪律：
- 标题用「名词 + 通知」，不用"提醒你一下"这类口语（微信模板审核偏好规整表述）
- 标签 3~4 个，**第一个永远是任务名称**，用户扫一眼就知道是哪件事
- 值要能独立成立："1/4 人已完成" 比 "1/4" 好
- 不塞隐私内容（不写详细地址、不放手机号）

### 7.2 四个模板

| templateKey | 标题 | 关键词（左侧标签） | 接收人 | 触发时机 |
|---|---|---|---|---|
| `TASK_ASSIGNED` | 任务委托通知 | 任务名称 / 委托人 / 参与人数 / 截止时间 | 每个参与者 | 创建成功、定时任务转 pending、被追加 |
| `TASK_REMIND` | 任务到期提醒 | 任务名称 / 委托人 / 截止时间 / 提示 | 未完成的参与者 | `deadline - remindMinutes`、手动催办 |
| `TASK_COMPLETED` | 任务完成通知 | 任务名称 / 完成人 / 完成时间 / 完成进度 | 委托人 | 任一参与者完成（且任务未结束） |
| `TASK_ALL_DONE` | 全员完成通知 | 任务名称 / 最后完成人 / 完成时间 / 完成情况 | 委托人 + 全体参与者 | `all` 模式最后一人完成 |

字段值样例：

```js
TASK_COMPLETED = {
  thing1: '周末大扫除',
  thing2: '小王',
  time3:  '2026-10-20 22:16',
  thing4: '1/4 人已完成'
}
```

字段类型约束（微信侧）：`thing` ≤20 字符（超出截断，需前端预截断）、`time` 建议 `YYYY-MM-DD HH:mm`、`phrase` ≤5 汉字、`number` 纯数字。

### 7.3 授权策略（决定留存）

微信一次性订阅：**一次授权 = 一次下发**。不能"发布时才弹"，必须攒。

| 用户动作 | 请求的模板 | 理由 |
|---|---|---|
| 布置任务点「发布」 | `TASK_ALL_DONE` + `TASK_REMIND` | 此刻最想"被回复/被提醒"，通过率最高 |
| 接受任务 | `TASK_ASSIGNED` + `TASK_REMIND` | 接受即承诺，愿意被打扰 |
| 标记完成 | `TASK_ASSIGNED` | 为下一条任务攒额度 |
| 打开「提醒设置」 | 四个模板批量 | 主动设置，通过率最高，可勾选"总是保持" |

规则：
1. 授权失败或被拒 **不阻断主流程**，接口照常提交
2. 每次最多 3 个模板（微信上限），用 `tmplIds` 数组一次请求
3. 结果全部上报服务端记账，用于设置页提示"待补 N 次"
4. 引导文案必须中性，禁止"不授权无法使用"

### 7.4 三层兜底

订阅消息不可靠时（拒授权、额度用尽、系统折叠），靠：

1. **小程序内消息中心**（`pages/messages/index/index`）：与微信卡片同构的列表，全部通知可回看，红点未读
2. **首页铃铛红点 + 液态玻璃 banner 的"1 件已逾期"**：进入即知
3. **任务详情 `onShow` 刷新**：状态变化实时可见

消息中心不是"备用方案"，而是产品的第二通知面。数据同源（`t_notice` 与订阅消息同一条记录），只是投递渠道不同。

## 8. UI 方案

### 8.1 设计风格

**关键词：暖、轻、有人味。**

不是企业协同工具（冷蓝 + 密集表格），也不是儿童打卡（高饱和 + 卡通）。取中间：**米白纸感底 + 珊瑚橘行动色 + 大圆角卡片 + 极轻阴影 + 一处液态玻璃**。信息密度中等，留白充分，像一张贴在冰箱上的便利贴。

三条执行原则：
1. **一屏一决策**：列表页只回答"有哪些事等我"，详情页只回答"现在该做什么"。
2. **状态用色不用形**：所有状态靠色块 tag 区分，不用不同形状的卡片。
3. **动作永远在拇指区**：主操作固定底部（`padding-bottom: env(safe-area-inset-bottom)`）。

### 8.2 配色

| 令牌 | 色值 | 用途 |
|---|---|---|
| `--brand` | `#FF6B4A` | 主按钮、选中态、进行中标识 |
| `--brand-ink` | `#D64C28` | 品牌色文字（保证 4.5:1 对比度） |
| `--brand-soft` | `#FFEDE7` | 品牌色浅底、选中 chip 背景 |
| `--mint` / `--mint-soft` | `#17A67C` / `#E4F6EF` | 已完成 |
| `--amber` / `--amber-soft` | `#E08A00` / `#FDF3E2` | 待接受 |

| `--danger` / `--danger-soft` | `#D64545` / `#FCEBEB` | 逾期、危险操作 |
| `--ink-1/2/3` | `#1E1B18` / `#6B625B` / `#A69C93` | 主/次/辅助文字 |

### 8.3 字体与尺度

系统默认字体（iOS 苹方 / Android 思源黑体），不引入自定义字体。

| 层级 | 字号 | 行高 | 字重 | 用途 |
|---|---|---|---|---|
| H1 | 40rpx | 56rpx | 600 | 页面标题 |

### 8.4 液态玻璃 banner（首页唯一装饰）

首页顶部是一块 236rpx 高的玻璃卡片，替代原"问候语"区块。它不是装饰性插图，而是**当日摘要**：几件事、几件已逾期、谁在等。

结构：

```
.glass-banner (236rpx, radius 44rpx, overflow hidden)
├─ .glass-banner-fill  折射源：四团径向渐变（品牌橘 / 薄荷绿 / 暖杏 / 浅粉）
└─ .glass              玻璃层：backdrop-filter + 渐变白 + 内外高光
   ├─ 今天 + 「1 件已逾期」胶囊
   ├─ 3 件事等你回应
   └─ 头像堆叠 + 「妈妈、小王在等你」+ 箭头
```

> 折射源最终用 `radial-gradient` 而不是「圆形 + `filter: blur()`」：`filter` 在部分安卓 WebView 不生效，色斑会变成硬边圆；径向渐变本身边缘就是柔的，任何机型都成立，且少一层合成。

WXSS 关键实现：

```css
/* 折射源：四团径向渐变，越靠边越浓，玻璃才有"折射到东西"的质感 */
.glass-banner-fill {
  position: absolute; inset: 0;
  background:
    radial-gradient(400rpx 400rpx at 2% -10%,  #ff5f35 0%, rgba(255,95,53,0) 62%),
    radial-gradient(380rpx 380rpx at 98% -12%, #1fc49b 0%, rgba(31,196,155,0) 60%),
    radial-gradient(520rpx 520rpx at 45% 118%, #ffae7e 0%, rgba(255,174,126,0) 66%),
    radial-gradient(320rpx 320rpx at 92% 114%, #ffd0c0 0%, rgba(255,208,192,0) 68%),
    #fff6f1;
}

.glass {
  position: absolute; inset: 0; border-radius: 44rpx;
  background: linear-gradient(135deg,
    rgba(255,255,255,.62) 0%,
    rgba(255,255,255,.20) 55%,
    rgba(255,255,255,.42) 100%);
  -webkit-backdrop-filter: blur(32rpx) saturate(190%);
  backdrop-filter: blur(32rpx) saturate(190%);
  border: 3rpx solid rgba(255,255,255,.92);
  box-shadow:
    inset 0 4rpx 0 rgba(255,255,255,.95),      /* 顶部镜面高光 */
    inset 0 -4rpx 16rpx rgba(255,255,255,.35), /* 底部厚度 */
    0 20rpx 52rpx rgba(190,90,60,.16);         /* 落影带一点品牌色 */
}
/* 左上镜面反射 + 右下二次折光 */
.glass::before {
  content: ''; position: absolute; inset: 0; border-radius: inherit;
  background:
    radial-gradient(280rpx 140rpx at 14% -10%, rgba(255,255,255,.9), transparent 70%),
    radial-gradient(180rpx 100rpx at 96% 108%, rgba(255,255,255,.55), transparent 72%);
}
```

四条纪律：
1. **玻璃里放结论，不放列表**。玻璃模糊会降低文字对比度，密集信息必须放在下方白卡。
2. **色斑要饱和**。玻璃靠"折射到的东西"体现质感，底色太淡会显得脏。用 `#FF5F35 / #1FC49B / #FFAE7E`。
3. **必须给降级**。`backdrop-filter` 在部分安卓 WebView 不生效：
   ```css
   /* 不支持时移除 blur，改用不透明渐变，保证可读性 */
   @supports not (backdrop-filter: blur(1px)) {
     .glass { background: linear-gradient(135deg, #FFE3D8, #FFF3EE); }
   }
   ```
4. **滚动行为**：列表上滑时 banner 透明度从 1 → 0、缩放 1 → 0.96（`transform` + `opacity`，用 `worklet` 或 `bindscroll`），避免占据屏幕。

性能：`backdrop-filter` 是合成层开销，整页**只允许出现一处**；不要给卡片加 blur，低端机掉帧。

### 8.7 状态设计（每个页面必须实现）

| 状态 | 表现 |
|---|---|
| 首次加载 | 骨架屏 3 张卡，不用全屏 loading |
| 下拉刷新 | 系统下拉，文案「松手刷新」 |
| 空态·收到 | 「暂时没人麻烦你」+「布置任务」 |
| 空态·发出 | 「还没派过活儿」+「让 TA 帮你记着」 |
| 空态·筛选 | 「这个状态下还没有任务」+「看全部」 |
| 空态·消息 | 「还没有通知」+「有事会在这里告诉你」 |
| 错误 | 图标 +「没加载出来」+「重试」 |
| 无网络 | 顶部黄条「当前网络不可用，显示的是上次内容」 |
| 提交中 | 按钮 loading + 禁用 +「发布中…」 |
| 提交成功 | 轻震动 + toast「已交给小王、陈陈，等 TA 们接单」 |

### 8.8 交互细节

1. **时间显示**：`今天 21:00` / `明天 08:00` / `周三 18:00`（7 天内）/ `10月28日 14:00`；逾期显示 `已逾期 2 小时`。
2. **接受任务**：按钮原地 loading → 状态色变化 → toast，**不跳页**，保持浏览连续性。
3. **拒绝**：底部 action-sheet「说一句」+ 3 个快捷理由（没空 / 不在家 / 做不了）。
4. **完成**：独立页（防误触），完成后 200ms 对勾描边 + `wx.vibrateShort`；`any` 模式下完成后立刻提示「你抢先做完了，其他人不用做了」。
5. **催一下**：仅委托人可见；点击后置灰 60 秒，文案变「已提醒」；只催未完成的人。
6. **看某人备注**：详情页点击参与者行 → 底部半屏显示备注与凭证图，不跳页。
7. **长按卡片**：快捷菜单（复制任务文案 / 撤回 / 删除）。
8. **滚动**：触底加载 `nextCursor`；banner 随滚动淡出。
9. **表单保护**：创建页填写后返回，二次确认「已填的内容会丢掉」。
10. **分享**：详情页 `onShareAppMessage` → `path=/pages/tasks/detail/index?id=xxx`，标题「妈妈 让你做：晾衣服」。

| 任一人完成 | 你抢先做完了，其他人不用做了 | 任务已结束 |
| 被拒绝 | 小王这次没接，换个人？ | 任务被拒绝 |

## 9. 埋点与验收

### 9.1 关键埋点

`login_success`、`task_create_submit`（含参与者人数、完成条件）、`task_accept`、`task_reject`、`task_complete`（含是否带图、是否抢首杀）、`task_remind`、`participant_add`、`subscribe_request`（含 accepted 数）、`notice_open`（从通知进入）、`friend_add_success`、`share_click`。

### 9.2 v1.1 验收标准

- [ ] 7 种任务状态 + 5 种参与者状态在 Mock 下均可复现，色值/文案与 5.3 一致
- [ ] `any` 模式：一人完成 → 任务 `completed`，其余 `skipped`，不再收到提醒
- [ ] `all` 模式：一人完成 → 仍 `in_progress`，进度正确；全员完成 → `completed` + `TASK_ALL_DONE`
- [ ] 全部拒绝 → 任务 `rejected`
- [ ] 同一人重复完成 / 非参与者操作 → 40900 / 40300
- [ ] 液态玻璃在 iOS 与安卓真机均可读；不支持 `backdrop-filter` 时有降级
- [ ] 服务通知四个模板字段与 7.2 一致，值不超过微信字符限制
- [ ] 消息中心未读数与铃铛红点一致，全部已读后可归零
- [ ] 页面中零 `wx.request`、零 URL 字面量（`grep` 可验证）
- [ ] 关闭 Mock 只改 `config/index.js` 一处即可对接后端
- [ ] 首屏冷启动 < 1.5s（中端安卓）；主包 < 1.5MB

### 9.3 迭代排期建议

| 阶段 | 内容 |
|---|---|
| M1（前端 v1.1） | 13 个页面 + 组件库 + Mock 全链路，可演示 |
| M2（后端接入） | SpringBoot 按第 6 章实现聚合与权限位，关闭 Mock 联调 |
| M3（消息） | 申请 4 个订阅消息模板，接 Redis 延时队列，真机验证触达与卡片样式 |
| M4（打磨） | 逾期提醒、好友申请消息、点赞反馈、暗色模式 |

### 9.4 审核风险与对策

| 风险 | 对策 |
|---|---|
| 头像昵称获取 | 用 `button open-type="chooseAvatar"` + `input type="nickname"`，不用已废弃的 `getUserProfile` |
| 订阅消息强制 | 拒绝授权必须可继续使用，文案中性；小程序内消息中心兜底 |
| 订阅模板被拒 | 标题用规整名词（"任务委托通知"），不承诺营销利益，不诱导 |
| 诱导分享 | 分享按钮不设奖励，不出现"分享给 3 个好友解锁" |
| 隐私协议 | 首次启动弹隐私协议，配置 `__usePrivacyCheck__`，说明收集头像昵称用途 |
| 类目 | 选「工具 - 效率」，不涉及交易，无需资质 |
